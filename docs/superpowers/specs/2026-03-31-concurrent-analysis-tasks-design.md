# 多任务并发分析设计

日期：2026-03-31

## 背景

当前系统已经具备单任务异步分析能力：

- 用户一次上传一批文件，后端创建一个 `AnalysisTask`
- `AnalysisTask` 通过 Celery 异步执行完整分析链路
- 前端提交后直接跳转到单任务详情页，围绕单个任务展示进度和结果

现状问题不在于后端完全没有异步能力，而在于产品交互仍然是“单次提交、单任务跟踪”。这会限制用户连续创建多个任务并同时观察多个任务的分析进度。

本次设计目标是让用户可以主动创建多个独立任务，每个任务上传一批文件，各任务在队列中独立并发分析。

## 目标

- 保持“一个任务对应一批文件”的现有语义不变
- 支持用户连续创建多个任务
- 支持多个任务同时进入异步队列并并发执行
- 提供任务总览页，统一展示多个任务的状态、步骤和结果入口
- 保留现有单任务详情页，用于查看某一个任务的细节

## 非目标

- 不把一个任务拆成多个子任务
- 不对单个任务内部步骤做并行化
- 不引入任务优先级、抢占式调度或取消能力
- 不在第一版引入 WebSocket 或 SSE 实时推送
- 不在第一版实现失败任务重试

## 用户场景

典型使用方式如下：

1. 用户进入任务中心
2. 用户上传一批文件并创建任务 A
3. 用户无需等待任务 A 完成，可以继续上传另一批文件并创建任务 B、任务 C
4. 后端将 A、B、C 分别作为独立任务入队
5. 任务中心持续展示多个任务的状态变化
6. 用户可随时进入单任务详情页或对应报告页查看结果

## 方案比较

### 方案一：保持任务语义不变，围绕任务中心增强并发能力

做法：

- 继续使用现有 `AnalysisTask` 作为核心任务模型
- 每次 `POST /tasks/` 创建一个任务，上传一批文件
- 新增任务列表接口和任务总览页
- 通过 Celery worker 并发消费多个任务

优点：

- 与当前数据模型和后端流程完全一致
- 改动集中在任务可见性和并发配置，风险低
- 最符合“用户自己创建多个任务”的业务定义

缺点：

- 需要补齐任务列表接口与总览页

### 方案二：一次提交拆成多个子任务

做法：

- 一次上传多个报告后拆成多个独立子任务
- 前端围绕批次和子任务展示状态

问题：

- 与本次需求不符，因为需求明确为“一个任务上传一批文件”
- 会引入额外的批次模型和更复杂的结果聚合

### 方案三：引入父任务编排子任务

做法：

- 使用父任务调度多个子任务并汇总状态

问题：

- 明显超出当前需求
- 增加调度复杂度，不利于当前系统快速演进

## 结论

采用方案一：保持现有任务定义不变，把“多任务并发分析”建设成任务中心能力。

## 架构设计

### 核心原则

- 任务是系统中的一等对象
- 并发单位是任务，不是文件，也不是分析步骤
- 详情与总览分离：总览负责多任务可见性，详情负责单任务深看

### 组件职责

后端：

- `AnalysisTask`：记录任务状态、当前步骤、时间戳和错误信息
- `Document`：记录任务关联文件
- `POST /tasks/`：创建任务并入队
- `GET /tasks/`：返回任务总览列表
- `GET /tasks/{task_id}`：返回单任务状态
- `GET /tasks/{task_id}/results`：返回任务结果摘要
- Celery worker：并发消费多个任务，但单任务内部保持串行

前端：

- 任务中心页：展示所有任务的状态、文件信息、结果入口
- 新建任务入口：允许用户继续创建新任务
- 单任务详情页：沿用现有步骤进度与结果展示
- 报告详情页：沿用现有报告展示逻辑

## 数据模型设计

### 保持不变的部分

继续沿用现有 `AnalysisTask` 与 `Document` 关系：

- 一个 `AnalysisTask` 对应多个 `Document`
- 任务状态仍使用 `pending / processing / completed / failed`
- 任务当前步骤仍使用现有步骤字段

### 建议补充字段

为提升任务总览可读性，建议补充以下能力：

- 可选增加 `display_name`
  - 含义：任务展示名称
  - 来源：用户创建任务时可选填写
  - 价值：任务列表中更容易区分不同批次材料

如果第一版不加 `display_name`，则前端使用以下临时规则生成任务标题：

- 显示首个文件名
- 若文件数量大于 1，则追加“等 N 个文件”

### 列表接口需要返回的聚合字段

任务列表项建议包含：

- `id`
- `status`
- `current_step`
- `created_at`
- `updated_at`
- `error_message`
- `document_count`
- `display_name` 或前端可生成标题所需的首文件名
- `report_id` 或 `has_report`

其中 `report_id` 可通过查询 `Report.task_id` 推导，不要求新增持久化字段。

## API 设计

### 保留接口

#### `POST /tasks/`

用途：

- 用户上传一批文件
- 后端创建一个 `AnalysisTask`
- 创建关联 `Document`
- 任务创建成功后触发异步分析

返回：

- `task_id`
- `status`

说明：

- 该接口语义不变
- 成功后前端不再强制跳转单任务详情页，而是回到任务总览页

#### `GET /tasks/{task_id}`

用途：

- 获取单任务状态、当前步骤和错误信息

说明：

- 继续服务于单任务详情页

#### `GET /tasks/{task_id}/results`

用途：

- 获取任务结果摘要、候选结果和报告 ID

说明：

- 保持现有语义，供单任务详情页使用

### 新增接口

#### `GET /tasks/`

用途：

- 返回任务总览列表

建议返回字段：

- `id`
- `status`
- `current_step`
- `created_at`
- `updated_at`
- `error_message`
- `document_count`
- `display_name`
- `report_id`

建议行为：

- 按 `created_at desc` 排序
- 第一版支持基础分页参数 `limit`、`offset`
- 可选支持 `status` 筛选，但不是首要需求

## 前端设计

### 页面结构

#### 任务中心页

职责：

- 作为用户默认工作台
- 展示多个任务并发执行状态
- 提供“新建任务”入口

页面元素：

- 上传卡片或新建任务弹层
- 任务列表
- 每个任务的状态标签
- 当前步骤文案
- 创建时间
- 文件数量或任务标题
- 查看详情按钮
- 查看报告按钮（仅已生成报告时显示）

交互规则：

- 用户创建任务成功后，停留在任务中心页
- 新创建任务插入列表顶部
- 任务中心页轮询刷新所有任务状态

#### 单任务详情页

职责：

- 展示某个任务的详细步骤进度
- 展示结果摘要和候选结果

说明：

- 沿用现有任务详情页逻辑
- 无需因为多任务支持而重构内部结构

#### 报告详情页

职责：

- 展示最终报告内容

说明：

- 继续沿用现有实现

## 数据流

### 创建任务流程

1. 用户在任务中心上传一批文件
2. 前端调用 `POST /tasks/`
3. 后端创建 `AnalysisTask`
4. 后端创建关联 `Document`
5. 后端调用 `run_analysis.apply_async(args=[task.id])`
6. 前端刷新任务列表并展示新任务

### 并发执行流程

1. 多个任务先后创建
2. 多个任务分别进入 Celery 队列
3. Celery worker 按并发配置同时处理多个任务
4. 每个任务独立更新自己的 `status` 与 `current_step`
5. 任务中心页轮询拉取整体状态

### 结果查看流程

1. 某个任务状态变为 `completed`
2. 任务中心页显示“查看详情”或“查看报告”
3. 用户进入单任务详情页或报告页查看结果

## 并发与配置设计

### 并发策略

- 任务之间允许并发
- 单任务内部步骤保持串行
- 并发度通过 Celery worker 配置控制，而不是写死在业务代码中

### 配置建议

建议引入显式并发配置，例如：

- `CELERY_WORKER_CONCURRENCY`

说明：

- 用于控制 worker 同时处理的任务数
- 部署环境可按机器资源调整
- 避免把并发策略散落在代码逻辑中

第一版不需要实现更复杂的：

- 队列分级
- 任务优先级
- 任务抢占
- 资源隔离调度

## 错误处理

### 基本原则

- 单个任务失败不影响其他任务继续执行
- 失败信息在任务总览和单任务详情中都应可见
- 错误需要尽可能保留明确上下文，便于后续排查

### 页面行为

任务中心页：

- 清晰展示失败态
- 展示 `error_message` 摘要

单任务详情页：

- 延续现有失败信息展示方式

第一版暂不包含：

- 失败任务重试按钮
- 批量失败重试
- 自动重试策略可视化

## 性能与风险

### 主要风险

1. 任务列表轮询会增加接口访问频率
2. 并发度提高后，LLM、OCR、检索等外部依赖压力会增加
3. 如果任务总览接口聚合查询不当，列表页性能会下降

### 缓解措施

- 任务总览页轮询间隔控制在 3 到 5 秒
- 列表页只返回必要摘要字段，不返回完整结果
- 通过配置项限制 worker 并发数
- 对列表接口做基础分页，避免无限增长

## 测试设计

### 后端 API 测试

- 创建任务后，`GET /tasks/` 能返回新任务
- 连续创建多个任务后，列表能返回多条记录
- 列表按创建时间倒序排列
- 列表字段包含状态、步骤、文件数量、报告入口信息

### 后端行为测试

- 连续提交多个任务时，每个任务都能独立入队
- 多个任务状态可以独立推进
- 某个任务失败时，其他任务仍可继续执行

### 前端验证

- 用户可以从任务中心连续创建多个任务
- 创建任务后页面停留在任务中心
- 总览页可以同时展示多个任务进度
- 已完成任务可以进入详情页或报告页
- 失败任务能展示失败状态与错误信息

### 本阶段不覆盖的测试

- WebSocket 实时推送
- 任务取消
- 任务优先级
- 失败任务重试

## 实施建议

建议按以下顺序落地：

1. 后端新增 `GET /tasks/` 列表接口
2. 后端补齐任务列表所需聚合字段
3. 前端新增任务中心页或将首页升级为任务中心
4. 前端调整创建任务后的跳转逻辑
5. 配置化 Celery worker 并发度
6. 补齐 API 与前端页面测试

## 开放问题

以下问题可以在实现阶段再决定，不阻塞当前设计：

- 第一版是否需要 `display_name`
- 首页是否直接承担任务中心职责，还是单独新增 `/tasks` 路由
- 任务列表使用卡片还是表格展示

## 结论摘要

本次需求应理解为“允许用户创建多个独立任务，并让这些任务在后台并发分析”，而不是“单任务内部多线程拆分”。因此，最合适的方案是继续复用现有 `AnalysisTask` 语义，补齐任务中心、任务列表接口和 worker 并发配置，把系统从单任务视角升级为多任务视角。
